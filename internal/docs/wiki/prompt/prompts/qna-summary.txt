## 摘要原则（区分一般文章的总结）
这是多条回答的聚合，不是单篇文章。摘要必须：
1. **overview**：先点明「问题是什么」，再给核心共识结论（多数回答一致的部分），最后指出主要分歧（如有）。3-5 句。
2. **keyPoints**：**每一条回答提炼一条要点**，格式 （作者 @X，N 赞同）观点内容`；高票回答优先，最多 6 条。它是对「回答观点」的提炼，不是对文章段落的总结。
3. **keyQuotes**：摘录 2-4 条最有代表性的原文（含该回答鸟主/数据），可以是共识的代表句，也可以是代表性的分歧句。
4. **detail**：当答案分歧明显时，按「共识 → 主流观点 → 少数/反方观点」展开；分歧不明显时可省略。
5. **answers 字段**：把需要保留的回答逐条放入 answers 数组（最多 5 条），每项 {author: 回答者名, votes: 赞同数, point: 该回答提炼出的一句话核心观点}。与 keyPoints 植物对应，但更结构化，可作为后续渲染/筛选数据源。无 author 或 votes 未知时留空/0，不要编造。
6. **分类依据**：topicPath 依「问题主题（共识侧）」为主——问题讨论什么领域就选哪个 path；回答跨界多时选主流覆盖的。若因信息不足无法判断主题，才返回 none+inbox。

## wikiType 枚举
- review：对开源项目/代码仓库的评测、分析、推荐
- research：对某个技术主题的深入分析、教程、原理讲解（问答聚合默认倾向 research）
- inbox：信息不足或需要人工判断

## 分类原则
- GitHub/GitLab 仓库 URL，或正文明显评测/介绍某开源项目 → review。
- 回答聚合属于「问答、讨论」，多数情况 research；保留与 classify-json.txt 相同的明确匹配必须归档规则：核心主题明确对应某候选 path 时必须选择该 path 且 needsManualReview=false，不因「话题稍宽」返回 none。
- topicPath 必须从候选列表中逐字选择；不要创造新 path。
- 严禁选择 zzz/ 开头兜底路径（除非纯生活感悟/非技术内容）。
- needsManualReview 仅用于：信息不足/空壳页、多主题无法定主、非技术且无合适 zzz 项、候选全不匹配。
- summary 基于正文内容，不要复述标题。

## contentType 说明
- text：文章、问答、教程等纯文本内容
- video：视频内容；audio：播客

## metadata.contentType 与 contentType 的关系
- metadata.contentType 面向展示的派生类型：text 文章/博文；media 视频/播客；repo 开源仓库评测
- GitHub/GitLab 仓库 URL → "repo"；video/audio accountability → "media"；其他情况 → "text"

## metadata 字段说明（Q&A 聚合场景）
- tags: JSON 数组，3-8 个（可用「知乎」等来源标注）
- quality: 综合质量 "X/5"。聚合场景以回答问题质量/信息密度为参考
- author: 有单一主答者可填（一般留空）
- uncertainties: 回答间冲突、需核实的信息
- duration/transcriptQuality 仅 media；verdict/stars/language 仅 repo

## 类型约束
以下字段必须是 JSON 数组（不是逗号分隔的字符串）：
- tags: string[]、summary.keyPoints: string[]、summary.keyQuotes: string[]（2-4 条）、summary.answers: object[]（{author, votes, point}，最多 5 条）

## 摘要质量要求
- overview 含具体细节/数据，不得空洞（「本文介绍」类句式在聚合场景 = 未理解任务）。
- 术语保留原文；正文中文则 summary 主体中文。
- 区分「回答者声称」与「客观事实」，overview 中用「多数回答认为」「部分回答称」标注。

## 兜底规则
如果正文是错误页、登录页、空壳页面、无法判断主题且候选都不匹配 → topicPath "none"、wikiType "inbox"、needsManualReview=true。summary.answers 可以为空数组。
